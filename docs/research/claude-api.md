# Research: claude-api

## Summary

I read the local claude-api skill docs (TS README, tool-use, streaming, files-api; shared tool-use-concepts, agent-design, prompt-caching, model-migration sections for Opus 5, Fable 5.1 refusals/preserved thinking and Opus 5.5, platform-availability, managed-agents overview/core/tools/environments/events/memory/scheduled-deployments/webhooks/client-patterns, error-codes, models). The findings for Gora's agent core are below.

(1) Build one manual, persisted, streaming agent loop on `client.beta.messages.stream(...)` with `finalMessage()`. It has to be the beta namespace because server-side fallbacks, compaction, the MCP connector, context editing, clear_at, per-message effort and mid-conversation tool changes are all beta. Use one merged `betas` array and Beta types throughout. Server-side fallback is `fallbacks: "default"` with the header `server-side-fallback-2026-07-01`. The array form needs exactly `-2026-06-01` instead, and mixing the two returns a 400.

(2) The docs default to the toolRunner and say approval gates work with it. Gora's gates can wait hours across restarts, though, and the runner is an in-memory iterator that also leaves pause_turn, refusal and max_tokens handling to you. So a SQLite-backed state machine fits better, and the docs allow this when control flow doesn't fit the runner's per-turn hooks. The loop must follow a few rules: put all tool_result blocks for one assistant turn in a single user message; return `is_error: true` for declined or invalid calls; validate input when `eager_input_streaming` is on (set it on custom tools only); handle pause_turn by re-sending with the paused assistant turn appended and no 'Continue' message; and check refusal before reading content.

(3) Server tools and their exact type strings: `web_search_20260209`, `web_fetch_20260209`, and code execution as `code_execution_20260120` (typed, non-beta) or `code_execution_20260521` (current, used with Skills). Files made by code execution come back as `bash_code_execution_output.file_id` and are downloaded through the Files API, which is now GA. The memory tool `memory_20250818` with `betaMemoryTool` is client-side and file-based, so it fits Muse-style memory ('forget this', provenance) poorly; structured memory of our own is the better fit. The MCP connector (`mcp-client-2025-11-20`, `mcp_servers[].authorization_token` plus an `mcp_toolset`) runs tools on Anthropic's side, and the docs show no per-call approval hook.

(4) Caching: keep top-level system and tools frozen and byte-identical for every user. Inject time, location and memories as `role: "system"` messages after the user turn; this is GA on Opus 5 with no beta header. Use an explicit 1h breakpoint on system plus top-level automatic caching for the tail, and keep TTLs ordered longest first.

(5) Correction to the task premise: the docs say the 400 on edited history (accounts created on or after 2026-08-31) applies to Claude Fable 5.1 and Claude Opus 5.5, not claude-opus-5. Gora should still keep history strictly append-only and store content verbatim. That makes a later move to the cheaper claude-opus-5-5 a config change, and it maximizes cache hits.

(6) Managed Agents offers per-session containers, permission policies (always_ask/auto), vaults with egress-time secret injection, limited networking, memory stores with versions and redaction, budgets, webhooks and cron deployments (1000 per org). The best way to use it is a hybrid: Messages API for chat in v1, and Managed Agents sessions for heavy 'cloud computer' background tasks.

Several details are not in the local docs and are listed at the end: the compaction trigger config, image and PDF size limits, TS timeout option names, typings for 'default' and clear_at, MCP result block names, and the browser toolset.

## Implications for Gora

- Agent core = one persisted manual loop on `client.beta.messages.stream(...)` + `finalMessage()`, with a module constant `BETAS = ['server-side-fallback-2026-07-01','compact-2026-01-12', ...]` and `fallbacks: 'default'` on every main-loop request. Use Beta types end to end, and put the SDK behind a small `LlmTransport` interface (stream -> text-delta callback + final BetaMessage) so everything runs against scripted fakes until keys exist. Fixtures should cover thinking blocks with signatures, pause_turn, refusal (pre-output and mid-stream), fallback blocks, compaction blocks, parallel tool_use and code-execution file outputs.
- Don't use toolRunner for the main loop. Implement a state machine per conversation: `running -> awaiting_tools -> awaiting_approval -> running -> done/refused/error`. Persist each assistant response verbatim BEFORE executing tools. Persist staged tool_results and pending approvals keyed by tool_use_id. Resume from a grammY callback_query in any process. Send all tool_results for a turn in ONE user message. Declines and timeouts become `is_error: true` results. Use tool_use_id as the idempotency key for side effects.
- SQLite schema must be append-only. The messages table (conversation_id, seq, role, content_json TEXT stored exactly as received or sent, kind, model, stop_reason, created_at) has no UPDATE and no DELETE on replayed rows. Store per-conversation frozen system_prompt_version, tools_hash, container_id and compaction watermark. Keep a separate usage log (input/cache_read/cache_creation/output, usage.iterations, model) and an audit_log (tool calls, approvals, evaluated permissions). Requests are rebuilt by concatenating rows only. Keep media as Files API file_id or base64, never Telegram URLs. Apply the fallback echo transform once at write time so replays are byte-stable.
- Prompt layout: the top-level `system` is a single static text block, byte-identical for ALL users, with an explicit `cache_control: { type: 'ephemeral', ttl: '1h' }`, plus top-level automatic `cache_control` for the tail (use ttl '1h' on both for chat, where Telegram reply gaps are often 5-60 min; keep longest-TTL-first).
